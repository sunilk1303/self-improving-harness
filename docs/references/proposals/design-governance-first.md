# Ledger-First Self-Improving Harness (LSIH): a governance-native architecture for an enterprise insights agent that improves itself as a regulated change-management process

> Design lens: **governance-first**. An enterprise-governance lens: self-improvement as a regulated change-management process.
>
> One of four independent design proposals generated during the design program. The synthesized architecture in `docs/` merges the winning proposal with grafts from the other three.

## Thesis

Self-improvement in an enterprise is not an optimization loop that happens to be logged — it IS a change-management process, so the audit ledger, policy engine, and evaluation service are the fixed trust kernel and the agent is merely a prolific, evidence-carrying PR author operating inside a declared, risk-tiered change envelope. Every improvement is an immutable event chain (limitation → proposal → gates → approval → promotion → outcome), which simultaneously satisfies EU AI Act Art 12/43 (pre-determined changes doctrine), NIST AI RMF, and rollback/forensics — while approval fatigue is managed as an explicitly budgeted, metered resource rather than an afterthought. We bet that Tier-0/Tier-1 artifact evolution (verified queries, playbook deltas, GEPA prompt evolution, semantic-model edits) captures 80% of the achievable gain (per GEPA/ACE/Snowflake evidence) at 1% of the risk and cost of code-level self-modification, which we defer behind dual-control gates.

## Architecture

Seven named components in three trust domains. TRUST DOMAIN A — THE KERNEL (immutable by the agent; separate repos, separate service identities, separate privilege rings): (1) THE LEDGER — an event-sourced, append-only audit store (Postgres event table, SHA-256 hash-chained records, daily Merkle-root anchoring to S3 Object Lock WORM storage). The logger runs as its own service; agents emit events via a write-only API and cannot read back, edit, or suppress entries (lesson from DGM fabricating logs). All harness state is a fold over this log — any historical harness configuration is reconstructible. (2) GATEKEEPER — an OPA/Rego policy-as-code engine sitting between every agent and every tool/data source; per-call evaluation returns allow / deny / require_approval(tier). Policies live in a Git repo the agent has zero write path to. Gatekeeper also classifies every improvement proposal into risk tiers T0–T3. (3) PROVING GROUND — the evaluation service holding the PRIVATE held-out golden sets (hidden question/answer pairs computed from frozen warehouse snapshots, per business objective). Exposes only Ladder-style thresholded accept/reject verdicts, never raw private scores. Runs candidate harnesses in Firecracker/E2B microVM sandboxes against snapshot replicas with fixed dollar budgets per evaluation. (4) APPROVALS DESK — a durable HITL queue (Temporal workflows; approvals survive restarts for days) with typed request kinds: change-approval, credential-grant, data-access-grant, metric-clarification, objective-disambiguation. TRUST DOMAIN B — THE SERVING PLANE: (5) ANALYST AGENT — the baseline insights harness: intent router → governed-metric resolver (dbt MetricFlow/Cube: answer by named metric when possible; fallback to generated SQL is itself a logged limitation signal) → NL-to-SQL stage (DSPy modules, sqlglot AST validation, EXPLAIN cost gate, read-only row/column-scoped credentials, on-behalf-of-user identity propagation) → hybrid RAG leg (permission-trimmed) → synthesis with mandatory numeric-claim grounding. Entire behavior pinned by a HARNESS MANIFEST — a Git-versioned lockfile pinning prompt versions, playbook version, tool versions, model IDs, retrieval params; deployment = repointing a manifest label; rollback = one label move (atomic, avoids partial-rollback incoherence). TRUST DOMAIN C — THE IMPROVEMENT PLANE: (6) FOUNDRY — the improver: Symptom Miner (limitation detection over OTel traces), Diagnosis Agent, Proposal Agents per improvement class (GEPA prompt evolver, ACE-style playbook curator, verified-query minter, semantic-model editor, skill synthesizer), and Dossier Builder, which compiles the mandatory evidence packet for every proposal. Foundry runs on Letta-style sleep-time compute — improvement work happens off the serving critical path; serving always uses the last promoted manifest. (7) RED TWIN — a frozen adversarial agent (different model family) that attacks every gate-passing candidate before promotion (see novel variations). All components emit OpenTelemetry GenAI spans (invoke_agent/chat/execute_tool) with span links from improvement episodes back to the triggering task traces; traces are for debugging, the Ledger is the record of authority.

## Improvement surface (what the system may modify about itself)

A four-tier declared change envelope, published in the technical documentation as EU AI Act Art 43(4) 'pre-determined changes' so in-envelope evolution never constitutes a substantial modification. TIER 0 — STANDARD (pre-approved, auto-apply after CI gates, log-only): append a Reflexion-style lesson to episodic memory (with provenance + tombstone semantics, never hard delete); add a retrieval few-shot example or synonym to the semantic layer; add a canary query; propose a verified query INTO THE REVIEW QUEUE (proposal is T0; activation is T1); ADD-only Mem0-style knowledge facts (UPDATE/DELETE of existing facts is T1). TIER 1 — NORMAL (async single-approver from the owning role, SLA 48h): GEPA-evolved prompt versions for any DSPy module; ACE playbook delta-merges (append/merge with dedup only — monolithic rewrites are banned to prevent context collapse); activating a verified query into the trusted-asset set; semantic-model edits (joins, column descriptions, custom instructions — the Snowflake-validated surface); router policy weight updates; plan-template library additions; retrieval pipeline parameter changes. TIER 2 — HIGH-RISK (maker-checker dual control: two human approvers from distinct CODEOWNERS groups, e.g., data owner + platform owner): minting a new parameterized skill/MCP tool from successful trajectories (new-tool admission is the tool-poisoning surface — always dual-gated, tool registered as a governed securable with per-call policy wrap); any agent-authored code touching pipeline stages; new metric DEFINITIONS (contested business logic); changes to the public eval set; requesting new data-source scopes or credentials (the agent can only file a request that blocks that branch — it can never mint access). TIER 3 — STRUCTURALLY IMPOSSIBLE (no write path exists, not merely forbidden by instruction): Gatekeeper policies, the Ledger, Proving Ground private sets and judge, its own tier-classification rules, approval-queue logic, model weights, production write credentials. The Replit incident is the design brief for T3: these are enforced by infrastructure separation, not prompts.

## Improvement loop

Step-by-step, every step an event in the Ledger. (1) TRIGGER: Symptom Miner runs as scheduled sleep-time jobs and real-time hooks, producing typed LimitationRecords (see limitation_detection) with severity, evidence trace IDs, and affected pipeline seam. Each record opens a LIABILITY in the limitation ledger (see novel variations — it cannot silently disappear). (2) SCHEDULE: an improvement scheduler picks which open limitation to work on using lineage-productivity scoring (HGM insight: immediate eval delta predicts poorly; we track which improvement lineages kept paying off per seam and allocate the fixed nightly Foundry budget there), weighted by severity and expected reviewer-minute cost. (3) PROPOSE: the class-appropriate Proposal Agent drafts ONE change scoped to a typed pipeline seam (Regimes pattern — a patch may only touch its declared interface), as a Git diff on a branch, plus a Dossier: failing trace IDs, root-cause hypothesis in natural language, the diff, predicted effect, blast-radius statement, and 'what could go wrong'. (4) STAGE-GATE CASCADE (cheap→expensive, expect ~90% rejection, so rejection must be cheap): G1 static checks — schema/lint/AST validation, policy pre-check, seam-scope verification, diff-size and complexity caps (anti dead-code accretion); G2 sandbox execution — candidate manifest runs in a microVM against snapshot replicas with mocked side-effects; zero policy violations is a hard fail; G3 PUBLIC eval — the golden dev slice the Foundry can see and legitimately optimize against; paired bootstrap CI over questions (~1000 resamples), multi-objective acceptance à la SICA: quality AND cost AND latency under the fixed per-eval dollar budget, across HETEROGENEOUS business objectives simultaneously (a change must not win on churn questions by regressing margin questions); G4 PRIVATE eval — Proving Ground scores on the hidden slice; returns only pass/fail (Ladder-thresholded); G5 RED TWIN attack — adversarial probe for Goodhart exploits (result recorded as the hacking-rate metric). (5) POLICY CLASSIFICATION: Gatekeeper assigns tier; T0 auto-merges with full logging; T1/T2 enter the Approvals Desk as evidence packets with active-engagement approval UI (see hitl_design); unclassifiable changes default-deny into T2. (6) DEPLOY: merged changes update the Harness Manifest; promotion moves the 'staging' label; SHADOW MODE runs the candidate manifest in parallel with production on live analyst queries (side-effect-free by construction — read-only credentials) for a window; an independent frozen judge plus mSPRT anytime-valid sequential test decides promotion the moment evidence suffices, minimizing shadow cost; the 'production' label then moves (cache invalidation forced — no stale-TTL windows). (7) MONITOR: canary queries hourly; per-seam quality dashboards; auto-rollback (emergency change, always allowed, retrospectively reviewed) if canaries regress; the LimitationRecord closes only when post-deployment telemetry confirms the symptom rate dropped — otherwise it reopens with the failed improvement attached to its lineage. (8) LEARN: accepted AND rejected proposals with their gate results are archived with lineage metadata (DGM-style archive = rollback store + audit genealogy + future proposal context).

## Limitation detection

Limitations are TYPED, machine-detected, and adversarially validated — never just self-reported by the model. Detector battery (each emits LimitationRecords with evidence): (a) EXECUTION FAILURES — SQL errors, empty result sets, timeout/EXPLAIN-cost-gate rejections, schema-binding failures; classified by a taxonomy mapped to pipeline seams (routing / schema retrieval / SQL gen / execution / synthesis) using MLflow-style trajectory scorers so improvements route to the right subsystem. (b) SILENT-ERROR PROBES — post-execution result validation: second-model sanity checks, row-count/sign/magnitude reconciliation against known aggregates, fan-out-join and NULL-semantics detectors on the AST; flagged answers become new golden candidates (the Ramp pattern: every confirmed failure becomes a permanent regression case). (c) METRIC-BY-NAME FALLTHROUGH — every time the governed-metric resolver fails and the agent falls back to raw SQL, that is a logged 'metric missing from semantic layer' limitation, the single cheapest high-yield signal (dbt: 83% vs 40%). (d) AMBIGUITY DETECTOR — when the same business noun ('revenue', 'active user') resolves to conflicting definitions across the semantic layer, retrieved docs, or past answers, a metric-clarification HITL request is filed; the loop is FORBIDDEN from resolving metric ambiguity by optimizing whatever is measurable (worst Goodhart surface per the research). (e) DRIFT MONITORS — nightly information_schema diff vs semantic model (schema drift); RAG corpus freshness deltas, coverage gaps vs the incoming question distribution, ACL-fidelity spot checks; hourly canary queries per source with drift alerting. (f) HUMAN SIGNALS — thumbs down, analyst corrections, and shadow-mode disagreements with the human's eventual action. (g) EVALUATION-INFEASIBILITY — 'we cannot backtest this recommendation class' or 'no outcome data access' is itself a first-class limitation triggering a data-access HITL request. (h) DETECTOR RECALL AUDITING — we do not trust the detector's own reports: scheduled fault injection deliberately breaks known things (poison a canary doc, rename a column in a sandbox replica, plant a wrong aggregate) and measures whether the Symptom Miner catches them; detector recall is a dashboarded metric, so 'fewer limitations reported' can never masquerade as 'fewer limitations existing'.

## Evaluation design

Core recipe adopted wholesale from the strongest evidence (AIDE²/Regimes/Kaggle): PUBLIC/PRIVATE SPLIT with budget caps and heterogeneity. (1) GOLDEN SETS per business objective, built from real analyst questions + expert-curated answers computed directly from frozen warehouse snapshots (InsightBench-style two-level scoring for narrative insights: summary-level + insight-level matching, plus mandatory numeric-claim extraction reconciled by re-executing queries — paraphrase never substitutes for correct magnitude/direction). Split three ways: PUBLIC dev slice (Foundry sees it, may overfit it); PRIVATE slice (held by Proving Ground; verdicts only, Ladder-thresholded to slow adaptive leakage; rotated quarterly from fresh production traffic because accept/reject bits deplete the set); SECOND-ORDER RESERVE — entire held-out business objectives touched only at quarterly release audits to verify improvements generalize beyond what was optimized. (2) SQL layer scored by test-suite execution accuracy: run candidate and reference queries across multiple perturbed snapshot instances (kills coincidental result-set collisions), normalized dataframe comparison, FLEX-style LLM semantic adjudication only on disagreements (lifts kappa 62→78). (3) LLM JUDGE RULES: frozen version-pinned judge from a DIFFERENT model family than the generator (self-preference bias becomes self-reinforcing in an RSI loop); rubric limited to fact-groundable criteria; order-randomized pairwise comparisons; length-normalized; calibrated against a 200–500-item human-labeled set with Cohen's kappa tracked, recalibration mandatory on any judge version change. The improver NEVER judges its own improvements. (4) STATISTICS: paired bootstrap CIs over eval items for offline gates (multiple generations per item to absorb LLM nondeterminism); mSPRT anytime-valid sequential tests for shadow-mode promotion (peek continuously without p-hacking, stop early to save eval dollars); one primary metric per gate with Bonferroni for guardrail metrics. (5) ANTI-GOODHART, LAYERED: private verdicts (most hacking collapses on unseen data); execution grounding (an insight not backed by re-executed queries across instances fails mechanically); RED TWIN adversarial probes; REWARD-HACKING RATE as a first-class dashboard metric measured by periodic human audit of a random sample of ACCEPTED improvements (AIDE² showed 34% residual hacking is the steady state after defenses — so continuous audit sampling is budgeted, not optional); trace-level anomaly detection (n-gram entropy of tool-call sequences, hard-coded-output detectors). (6) MULTI-OBJECTIVE GATE: quality AND dollar cost AND p95 latency, evaluated across heterogeneous objective families under a fixed per-evaluation budget — improvements cannot win by spending. (7) DECISION QUALITY (no ground truth): Brier-scored probabilistic claims (strictly proper — ungameable except by being right; report the reliability/resolution decomposition to expose base-rate hedging), expert-labeled golden decision sets created at objective-definition time, and backtesting/uplift-Qini on holdouts where intervention logs exist.

## Audit design

Event-sourced, hash-chained, externally anchored, agent-unwritable. RECORD SCHEMA — every event carries: event_id, monotonic sequence, timestamp, SHA-256 of previous event (chain), actor identity (per-agent SPIFFE ID, human SSO identity, or service identity — never shared API keys), event_type, and a typed payload. Event types covering the full lifecycle: LimitationDetected {taxonomy class, severity, evidence trace IDs, affected seam}; ProposalDrafted {diff hash, seam, dossier URI, lineage parent}; GateResult {gate id G1–G5, verdict, metric values, bootstrap CI / p-value, eval-set version, dollar cost}; PolicyDecision {Rego policy version hash, tier assigned, decision}; ApprovalRequested / ApprovalGranted {approver identities, latency, engagement-check result, selected reason code}; ManifestPromoted {from-manifest hash, to-manifest hash, label, shadow-mode statistics}; CanaryAlert; RollbackExecuted {trigger, restored manifest hash}; MemoryMutation {ADD/UPDATE/DELETE/NOOP with tombstones — memory writes get event-sourced undo because config rollback alone does not revert state}; CredentialRequest / Grant; ClarificationRequest / Resolution; HackingAuditSample {auditor, verdict}. STORAGE: append-only Postgres event table as the hot store; each record HMAC-signed (keys in an HSM/KMS outside all agent domains); hourly Merkle roots anchored to S3 Object Lock (compliance mode) and optionally a transparency log — any post-hoc edit breaks every subsequent signature. The logger service runs in the kernel trust domain: agents hold a write-only, non-repudiable emit path and no read/update/delete path (hash chains prove integrity, not completeness — so suppression is prevented by privilege separation, and gate/policy services independently write their own events rather than trusting agent self-reports). EVIDENCE PACKETS: every T1+ change gets a compiled, immutable dossier (diff, motivating traces, all gate results with statistics, Red Twin report, approver identities and reason codes, deployment and post-deployment outcome) — this is the artifact handed to auditors and maps 1:1 to EU AI Act Art 12 logging and Art 43 pre-determined-change documentation; the RMF mapping is explicit in the docs (GOVERN=Gatekeeper+roles, MAP=Symptom Miner, MEASURE=Proving Ground, MANAGE=rollback+incident flow). QUERYABILITY: a read-model projection supports 'what did the harness believe/contain on date D', full lineage walks (limitation → attempts → accepted change → outcomes), and a governance API (current manifest inventory, change feed) for enterprise control-tower platforms (ServiceNow-style) to consume. Content capture is tiered by risk with PII redaction processors before persistence; OTel traces remain the debugging layer and are never the record of authority.

## Human-in-the-loop design

Humans are pulled in at exactly five typed junctures, all flowing through one durable async Approvals Desk (Temporal workflows: the blocked improvement branch parks as a persisted checkpoint for hours/days while serving continues on the unmodified manifest; decisions resume the branch via signal): (1) T1 change approvals — single approver from the owning role (prompt changes → platform owner; semantic-model edits → data steward), 48h SLA, then escalation, then expiry-with-reopen. (2) T2 approvals — maker-checker dual control, initiator ≠ approver, two humans from DISTINCT CODEOWNERS groups (data owner + platform owner), implemented as branch protection with 2 required reviewers; reserved surgically (new tools, code, new data scopes, metric definitions) because dual control burns 2x scarce capacity. (3) Credential/data-access grants — the agent structurally cannot mint access; it files a typed request; that improvement branch blocks until a human grants scoped, read-only, expiring credentials through the normal IAM process; grant recorded in the Ledger. (4) Objective/metric clarification — 'maximize revenue' ambiguity (horizon? segment? bookings vs recognized?) is a first-class request type answered by the business owner, and the answer is codified as a governed metric definition (T2) so it is answered once, not per-query. (5) Hacking-audit sampling — scheduled human review of a random sample of accepted improvements. ANTI-FATIGUE DESIGN (the research says more oversight can be less safety — realized safety is an inverted-U in escalation volume): reviewer capacity is a DECLARED BUDGET (e.g., 30 min/day per role); the scheduler meters escalations against it and batches low-urgency T1 proposals into a daily digest rather than interrupt-per-item; the T0 class is made as large as safely possible so humans only see genuinely ambiguous/high-stakes items. ANTI-RUBBER-STAMP DESIGN (explainability paradox: clear AI rationales INCREASE deference): the approval UI leads with the raw diff and evidence, not the agent's narrative; the approver must pass an auto-generated engagement check (a factual question derivable only from the dossier, e.g., 'which two tables does this verified query join?') and select a structured reason code before the Approve button activates; approve-rate and decision-time are themselves Ledger metrics with an automatic alarm at >95% approval with sub-10-second median decisions — a firing alarm freezes T1 auto-routing and triggers a governance review. Queue-starvation safety: blocked branches never silently auto-approve under load (that recreates Replit); they expire and reopen as aged liabilities, and starvation shows up on the limitation-ledger aging dashboard.

## Novel variations

- APPROVAL FUTURES (pre-authorized change budgets): instead of per-item approval, data stewards periodically approve bounded, template-scoped change ALLOWANCES — e.g., 'up to 5 verified-query activations per week matching the read-only single-schema template, auto-expiring in 90 days'. Each allowance is itself a Ledger event and is the operational embodiment of EU AI Act Art 43(4) pre-determined changes: the envelope is explicitly declared, consumption is metered against it, and exhaustion or template deviation falls back to per-item review. This converts approval from a per-change tax into a periodic portfolio review, directly attacking fatigue without widening risk — and the steward's renewal review of 'what did last quarter's allowance actually get spent on' is a natural audit ritual.
- LIMITATION DOUBLE-ENTRY LEDGER with detector fault-injection: every detected limitation opens a LIABILITY that can only be closed by (a) a promoted improvement whose post-deployment telemetry confirms the symptom rate dropped, (b) an explicit human waiver with reason code, or (c) aged expiry that reopens at higher severity. Nothing disappears silently, so the Symptom Miner cannot Goodhart its own metric by under-reporting — and to prove it isn't blind rather than merely quiet, a scheduled fault-injection harness plants known defects (poisoned canary doc, renamed sandbox column, deliberately wrong aggregate) and scores detector RECALL as a dashboard metric. The limitation detector is thus evaluated exactly like the agent it monitors.
- RED TWIN adversarial promotion gate: a frozen, hand-tuned attacker agent (different model family, never self-improving, part of the kernel trust domain) receives every gate-passing candidate and spends a fixed budget trying to make it produce a confidently wrong but judge-pleasing insight: perturbed schemas, adversarial phrasings of golden questions, bait questions whose plausible-looking answer is known-false from the snapshot. Its success rate IS the production reward-hacking metric (AIDE² tracked hacking post-hoc; we make it a promotion gate), and because the Twin is frozen and separate, the improving agent cannot co-adapt with its own examiner.
- BRIER LEDGER for decision accountability: every recommendation the agent ships must embed at least one falsifiable probabilistic claim ('P=0.7 that churn in segment X drops 2-4pts within 90 days if Y'), appended to the immutable log BEFORE outcomes are knowable and non-editable afterward. As outcomes mature, a scheduled job scores the rolling Brier ledger with reliability/resolution decomposition (strictly proper scoring — the one metric class the agent cannot game except by actually being right, and base-rate hedging is exposed by the resolution term). Sustained miscalibration in a claim category automatically opens a limitation liability, closing the loop between long-horizon decision quality and the fast improvement cycle.
- ENVELOPE-CREEP RE-BASELINING (the identity problem): no single in-envelope change is substantial, but their composition can be — so quarterly, the CURRENT manifest and the ORIGINAL assessed baseline are both replayed against the frozen second-order reserve suite plus a behavioral-invariant checklist (access footprint unchanged, answer distribution shift bounded, no new side-effect classes), and the aggregate diff is reviewed as if it were one big change. If cumulative drift exceeds declared bounds, the system is formally re-baselined (new conformity documentation) before further T1 auto-routing resumes. This is the audit answer to 'a thousand small approved changes quietly became a different system'.
- REVIEWER-MINUTE MARKET for improvement scheduling: open limitations and pending proposals bid for the scarce declared reviewer-capacity budget, priced by tier (T2 costs 2 approvers) and prioritized by HGM-style lineage productivity (expected downstream value of the seam's improvement lineage) per reviewer-minute consumed. This fuses the anti-fatigue budget and the anti-greedy scheduling insight into one allocator: human attention flows to the improvement lineages with the best evidence of compounding payoff, not to whichever proposal arrived last.

## Risks

- Approval fatigue and queue starvation despite metering: if stewards don't clear the queue, the improvement loop silently freezes (glacial velocity) — mitigated by allowances, digests, aging dashboards, and SLA escalation, but an org that won't staff review capacity gets a static harness; this must be a stated operating cost, not a surprise.
- Residual reward hacking is the steady state, not zero (AIDE²: 34% after defenses): budget for permanent human audit sampling of accepted changes; the Red Twin and private sets reduce but never eliminate it, and business metrics like 'revenue impact of insights' are far more gameable than SWE-bench.
- Private eval-set depletion via adaptive accept/reject leakage (Blum-Hardt): with ~90% rejection and many proposals, the hidden slice becomes effectively public — quarterly rotation from fresh traffic is mandatory OPEX, and one engineer with read access to the private set silently destroys the guarantee (enforce via IAM and access-log review).
- Sandbox-to-production fidelity gap: changes that pass on snapshot replicas break on live permission structures, data distributions, or schema drift — shadow mode narrows this but doubles inference cost during windows, and snapshotting warehouse data into sandboxes creates its own PII/data-governance problem requiring masked or synthetic replicas.
- State contamination on rollback: manifest rollback does not revert memory/vector-store writes made by a bad improvement — memory mutations need their own event-sourced undo (tombstones, versioned blocks), which is engineering-heavy and easy to shortcut.
- Envelope creep and governance erosion: sustained pressure to reclassify T1 changes as T0 'because the gate always passes' recreates the Goodhart gate; tier reclassification must itself be a T2 dual-control change, and quarterly re-baselining is the backstop.
- Judge and golden-set decay: schema drift, question-distribution drift, and silent judge model updates rot the evaluation core — pin judge versions, recalibrate kappa on schedule, refresh goldens from production traffic, or the gate becomes theater.
- Cost blowout: staged gates, shadow windows, multi-instance execution checks, and Red Twin attacks all cost real dollars per proposal at ~90% rejection — the fixed per-eval budget and anytime-valid early stopping contain it, but the org must accept low accepted-change throughput as the price of trustworthy gains.
- Reviewer disagreement noise (kappa ~0.52 on 'risky'): single-reviewer T1 gates are lottery-like for ambiguous changes; route detected ambiguity to dual control, accepting the capacity hit.
- Scope discipline: L2 'ignition' (the improved system becoming a better improver) has never been demonstrated (AIDE² tested and failed) — this design promises L1 only (the harness improves its own task pipeline under a fixed, hand-tuned improver); stakeholders sold L2 will be disappointed.

## MVP scope

BUILD FIRST (12–16 weeks, one team): (1) Baseline serving harness: intent router + governed-metric resolver over dbt MetricFlow or Cube + DSPy NL-to-SQL stage with sqlglot AST validation, EXPLAIN cost gate, read-only scoped credentials + one hybrid-RAG knowledge-base leg with permission trimming; OTel GenAI instrumentation from day one. (2) The Ledger (Postgres event store, hash chain, S3 Object Lock anchoring, write-only emit API) and the Harness Manifest with label-based deploy/rollback — these come FIRST because retrofitting audit is impossible. (3) Golden set v1: 150–300 curated questions across 2 business objectives from frozen snapshots, public/private split, execution-based scoring plus one frozen different-family judge with a 200-item human calibration set. (4) Improvement classes T0 + T1 ONLY: verified-query mint-and-activate, ACE-style playbook deltas, nightly GEPA prompt evolution ($2–10/run makes this economically trivial); PR-author pattern on GitHub with CI eval gates and branch protection. (5) Symptom Miner v1: SQL failure taxonomy, metric-fallthrough logging, schema-drift diff, hourly canaries, thumbs-down capture. (6) Approvals Desk v1: Temporal-backed async queue, one approver role, engagement-check UI, approve-rate/decision-time alarms. (7) Shadow mode with mSPRT promotion for manifest changes. FEASIBILITY EXPERIMENTS SHIPPED WITH MVP: (a) baseline vs self-improved accuracy curve over 6 weekly cycles on the private slice (expect baseline 10–30% per Spider 2.0 reality; harness-level gains carry most headroom); (b) measured rejection rate and cost per accepted improvement; (c) detector-recall fault-injection study; (d) approval-latency/fatigue telemetry. EXPLICITLY DEFERRED: T2 skill/MCP tool minting and any agent-authored code (needs the Red Twin and dual-control machinery matured); Red Twin (phase 2 — MVP uses human hacking-audit sampling instead); multi-source federated query planner (start with one warehouse + one KB); HGM lineage scheduler (MVP uses severity-ordered FIFO); backtesting/OPE and the Brier ledger (needs outcome-data plumbing); cross-instance skill sharing; approval-futures allowances (needs baseline approval-volume data to size them); weight-level anything (permanently out of scope — SEAL's forgetting curves and unauditability rule it out).

## Tech stack

Python 3.12. Serving/orchestration: LangGraph for agent graphs with interrupt()+checkpointer, Temporal (+ official LangGraph integration) for durable HITL workflows and sleep-time Foundry jobs. LLMs: Claude (Opus/Sonnet) for generation and Foundry proposal agents; a different-family pinned model (e.g., GPT-class or Gemini-class) as the frozen judge and Red Twin — cross-family separation is a design requirement, not a preference. Prompt/program optimization: DSPy with dspy.GEPA; playbook curation per ACE (append/merge deltas). Semantic layer: dbt MetricFlow (Apache 2.0) or Cube, exposed via MCP; tool registry as catalog-governed MCP (Unity-Catalog-style securables where the platform offers it). SQL safety: sqlglot AST validation, EXPLAIN gates, per-source read-only scoped credentials, DB-level RLS via session variables (enforcement in the database, never the LLM). Policy: OPA/Rego sidecars, policies in a locked Git repo, default-deny for unclassified actions. Ledger: Postgres append-only event table + HMAC signing (AWS KMS/HSM) + hourly Merkle anchoring to S3 Object Lock compliance mode. Observability: OpenTelemetry GenAI semantic conventions exported to self-hosted Langfuse (data residency) with PII-redaction processors; Langfuse prompt versions + labels for prompt artifacts, all pinned inside the Git-versioned Harness Manifest (the atomic rollback unit). Sandboxing: Firecracker microVMs via E2B (or Kata on k8s) for candidate evaluation against masked snapshot replicas; gVisor acceptable for lower tiers. Eval statistics: paired bootstrap (scipy/numpy) offline, mSPRT/confidence-sequences (Eppo-style GAVI implementation) for shadow promotion. CI/CD: GitHub PRs, branch protection with CODEOWNERS dual-review for T2, eval gates in Actions runners calling the Proving Ground API. Identity: SPIFFE/SPIRE per-agent workload identities, human approvals via enterprise SSO (OIDC) so every Ledger actor field is non-repudiable.
