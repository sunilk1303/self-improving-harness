# GateKit: A Deploy-Grade Self-Improving Harness for Enterprise Insight Agents

> Design lens: **production / SRE**. A platform-engineering lens: every self-improvement is a software deploy with gates, canaries, and rollback. **Selected as the winning design by a unanimous 3-judge panel.**
>
> One of four independent design proposals generated during the design program. The synthesized architecture in `docs/` merges the winning proposal with grafts from the other three.

## Thesis

Every self-improvement is a software deploy, full stop: an immutable, versioned Harness Manifest change that must pass a staged eval pipeline (public/private split, fixed dollar budget), roll out via shadow-then-canary, and be revertible in one label repoint in under 60 seconds — with the eval service, policy engine, and audit log living outside the agent's privilege boundary so regressions cannot ship silently and evidence cannot be fabricated. The counter-risk of a frozen loop is handled structurally, not by hope: gate width is governed by a two-sided error budget (a regression budget that shrinks the auto-apply class when spent, and an improvement-velocity SLO that widens it when regressions stay unspent), so the system earns autonomy from its own track record the way a service earns reduced change-review over time.

## Architecture

Nine named components in three trust domains. SERVING DOMAIN (agent-writable state only via gated deploys): (1) Insight Agent Runtime (IAR) — the baseline harness: a Router module (question → governed-metric lookup | NL→SQL | RAG | federated plan), NL→SQL Generator, Retrieval leg (hybrid BM25+dense+rerank, permission-trimmed), and Synthesizer, each implemented as a DSPy module so prompts/instructions are optimizable artifacts; all data access goes through MCP tools registered in (2) the Tool Registry (catalog-governed, on-behalf-of-user auth, per-call policy check). (3) Harness Manifest — a lockfile (Git-versioned, content-hashed) pinning every prompt version, playbook version, tool version, model ID, retrieval params, and memory-snapshot ref; the running system is always reconstructible from one manifest hash; environment labels (prod, canary, shadow, staging) are movable pointers to manifests. IMPROVEMENT DOMAIN: (4) Flight Recorder — OTel GenAI semconv traces (invoke_agent/chat/execute_tool spans) into ClickHouse; every span carries the serving manifest hash. (5) Limitation Ledger — typed LimitationEvents emitted by detectors, each linking to evidence trace IDs. (6) Improvement Factory — sleep-time proposer that drafts exactly one change per proposal as a PR against the manifest repo, scoped to a declared 'seam' (Regimes-style typed interface); it has no write access to anything else. (7) Deployment Controller — repoints labels, orchestrates shadow/canary/fleet rollout, executes auto-rollback on SLO breach. CONTROL DOMAIN (agent has zero write access, separate repo/process/credentials): (8) Gatehouse — the eval service holding golden sets, the private held-out slice, frozen judge, sandbox fleet (gVisor/Firecracker) and frozen warehouse snapshots (lakeFS branches); returns accept/reject plus public-slice numbers only. (9) Policy Kernel (OPA/Rego sidecar) + Approval Queue (Temporal workflows) + Audit Chain (hash-chained append-only event log anchored to S3 Object Lock WORM). The maxim enforced by IAM, not prompts: the improver authors PRs; the control domain decides; the audit chain records; the agent can read none of the control domain's internals.

## Improvement surface (what the system may modify about itself)

Four tiers, each an enumerated change type with a declared seam (this enumeration doubles as the EU AI Act Art 43(4) 'pre-determined changes' envelope). TIER 0 — standard changes, auto-apply after CI evals, log-only: add a verified query (human-confirmed question→SQL pair) to the VQR; append an ACE-style playbook delta item (dedup-merged, never monolithic rewrite); add a retrieval few-shot example; add a glossary synonym; add a canary probe. TIER 1 — auto-apply after full Gatehouse gate + canary rollout: prompt/instruction versions for any DSPy module (GEPA-evolved offline); tool descriptions; router policy weights; retrieval params (k, reranker thresholds, chunking config); plan templates. TIER 2 — human approval required (async queue, single approver): minting a new MCP tool from verified successful trajectories (parameterized SQL/retrieval skill); semantic-layer metric definition proposals; promotion of new questions into the golden set; memory consolidation ops (Mem0-style UPDATE/DELETE — always tombstoned, never hard-deleted). TIER 3 — dual control (maker-checker, two approvers from distinct CODEOWNERS groups: data owner + platform owner): new data-source scopes or credentials; any agent-authored executable code; model version changes; changes to objective definitions. PERMANENTLY OUT OF SURFACE (enforced by repo permissions and the Policy Kernel, not policy text): the Policy Kernel and its Rego rules, the Gatehouse and all private eval data, the Audit Chain, the tier classification itself, and the agent's own IAM grants. Tier membership of a change TYPE is itself movable only by humans — but see the trust-ladder mechanism below for how movement is triggered by data.

## Improvement loop

TRIGGER: (a) nightly sleep-time batch when the Limitation Ledger accumulates events above per-type thresholds; (b) immediately on canary-probe regression or schema-drift alarm; (c) weekly scheduled GEPA optimization runs per module. A bandit scheduler picks WHICH limitation to work, scored by lineage productivity (HGM CMP-lite: credit accrues to limitation-types whose past fixes survived 30 days in prod) times event frequency times estimated fix cost — not by immediate eval delta. PROPOSE: Improvement Factory reads the evidence traces, writes a diagnosis, and opens ONE PR: manifest diff + machine-readable ChangeRecord (limitation evidence trace IDs, change type/tier, predicted effect, self-authored rollback runbook, and 2–3 new canary probes that would detect this change regressing). EVALUATE (staged, cheap→expensive, fixed dollar cap per candidate, hard-stop): S1 static — sqlglot AST checks, schema lint, policy pre-flight, diff-size and dead-code lint (reject baroque diffs); S2 sandbox — replay 25 fixture queries in a gVisor sandbox against lakeFS snapshot data with mocked side effects, zero policy violations tolerated; S3 public gate — full public golden slice, paired bootstrap CI (1000 resamples, multiple generations per item) must exclude zero on the primary metric with no slice regressing >2pts; S4 private gate — Gatehouse runs the private held-out slice + tripwire probes and returns only ACCEPT/REJECT (Ladder-style thresholded bit, no scores), decrementing that slice's leakage budget. Expect ~90% cumulative rejection; rejections are cheap (most die at S1–S2) and every rejection is an audit event. GATE: Policy Kernel classifies the tier → Tier 0/1 auto-merge on green; Tier 2 parks as a durable Temporal workflow in the Approval Queue; Tier 3 requires two distinct approvals. A merged PR bumps the manifest version. DEPLOY: Deployment Controller first runs the 3am drill (staging rollback rehearsal must complete <60s or promotion is blocked), then shadow (new manifest answers the live query stream unserved for ≥200 queries; frozen different-family judge compares paired outputs, mSPRT anytime-valid monitor), then canary label at 10% of traffic with auto-rollback wired to: judge-preference inversion, hallucination/grounding-check failures, p95 latency, per-query cost, and the change's own shipped canary probes; then fleet label repoint (with Langfuse cache invalidation to close the stale-TTL window). MONITOR: hourly canary probes per data source, reward-hacking rate dashboard, weekly human audit sample of 5 accepted changes; 30-day survival feeds the CMP-lite scheduler and the trust ladder. Every step of all of the above is an event on the Audit Chain.

## Limitation detection

Limitations are typed, machine-emitted events — never the agent's self-report. Detector inventory, each mapping to a limitation class from the brief: (1) EXECUTION DETECTORS: SQL errors, empty result sets, EXPLAIN cost-gate rejections, statement timeouts → weak-query-generation events with the failing SQL attached. (2) FALLBACK DETECTOR: every time the Router falls back from governed-metric-by-name to raw SQL generation, emit metric-gap event ('metric X missing from semantic layer') — the highest-value signal because its fix (a proposed metric definition) has a natural Tier 2 HITL gate. (3) DRIFT MONITORS: nightly information_schema diff vs semantic model (schema drift); corpus freshness deltas and coverage-gap analysis of incoming question embeddings vs indexed content (RAG staleness/coverage); ACL-fidelity probes (a permission-widening result is a SEV, not a limitation). (4) GROUNDING DETECTOR: post-hoc numeric-claim extraction from synthesized insights, reconciled by independently re-executing queries; mismatch → reasoning/synthesis limitation. (5) DISAGREEMENT DETECTOR: for questions answerable by two sources, sampled dual-execution; divergence → routing or join-path limitation. (6) HUMAN SIGNALS: thumbs-down, analyst corrections, and clarification-question frequency per topic (high ambiguity rate on a term → ambiguous-metric event routed straight to HITL clarification, never resolved by the loop itself). (7) EVAL-DERIVED: golden-set failures localized by trajectory-level scoring to the failing stage (retrieval vs SQL-gen vs synthesis), MLflow-style. Every detector writes a LimitationEvent{type, evidence_trace_ids, frequency, first_seen, cost_of_failure_estimate} to the Ledger. Anti-gaming invariant: the loop's success metric is never 'fewer limitations reported' — detectors run in the control/observability plane the agent cannot modify, and detector-volume drops trigger an alert, not a celebration.

## Evaluation design

Three-slice eval architecture inside the Gatehouse (a separate trust domain — separate repo, separate service account, no agent read access). PUBLIC SLICE: ~300 golden questions with verified answers computed from frozen lakeFS warehouse snapshots, visible to the Improvement Factory as its optimization signal; grown Ramp-style — every production failure becomes a permanent case. PRIVATE SLICE: held-out questions the improver never sees; results reported only as an accept/reject bit past a noise-calibrated threshold (Ladder pattern); each query against it decrements an explicit LEAKAGE BUDGET (metered adaptive-data-analysis accounting) and exhaustion auto-triggers rotation from freshly labeled production traffic. SECOND-ORDER RESERVE: 1–2 whole business objectives / data domains never used in any loop, evaluated only at quarterly release audits to verify improvements generalize. Scoring stack per question, cheapest-first: execution-based result-set comparison across multiple perturbed DB instances (test-suite accuracy, order/duplicate-normalized — plain EX alone has ~9% FP / ~17% FN); FLEX-style semantic judge only on disagreements; for narrative insights, a two-level judge (summary + insight-matching, G-Eval rubric with fact-grounded criteria) that is a FROZEN, PINNED, DIFFERENT-MODEL-FAMILY judge, kappa-calibrated quarterly against 200 human-labeled examples, order-randomized and length-normalized. Anti-Goodhart measures, layered: (a) the public/private split itself, with heterogeneous objectives per eval so a change must win across families; (b) fixed dollar budget per evaluation so brute-force spend can't masquerade as improvement; (c) TRIPWIRE PROBES — honeypot questions whose plausible-sounding answer is wrong unless the data is actually queried (e.g., a metric whose sign flipped in the snapshot); passing public while failing tripwires flags the proposal as a hack, increments the first-class reward-hacking-rate metric, and quarantines the proposing lineage; (d) grounding reconciliation — every numeric claim in an accepted answer must match independent re-execution; (e) weekly human audit of a random sample of accepted improvements (budgeted, non-optional — 34% residual hacking after defenses is the published steady state, so assume nonzero forever); (f) statistics that survive peeking — paired bootstrap CIs offline, mSPRT/anytime-valid tests for shadow and canary, one designated primary metric with Bonferroni on the guardrail metrics.

## Audit design

Two-layer records: OTel traces for debugging (mutable, rich, PII-redacted at the collector), and the Audit Chain as the record of authority — an append-only Postgres event table where each event carries SHA-256 of (payload ‖ previous hash), batched and anchored hourly to S3 Object Lock (compliance mode WORM) so tampering with any historical entry is externally detectable. The logger runs in the control domain; the agent physically cannot suppress or fabricate entries about itself (the DGM fabricated-logs lesson). Canonical ImprovementRecord schema: {change_id, proposal_ts, limitation_event_ids[], evidence_trace_ids[], change_type, tier, seam, manifest_hash_before, manifest_hash_after, unified_diff, predicted_effect, eval_results{stage_outcomes, public_scores+CIs, private_accept_bit, tripwire_result, dollar_cost, judge_version}, policy_decision{rule_id, verdict}, approvals[{approver_identity, role, decision, stated_reason, decision_latency_ms}], deploy_events[{label, ts, shadow_stats, canary_stats}], rollback_runbook_ref, shipped_canary_probe_ids[], rollback_events[], survival_status}. Every event also lands as the PR record in Git (human-browsable mirror), and every serving trace carries its manifest hash, so 'which change caused this wrong answer at 3am' is one join: trace → manifest → ImprovementRecord → evidence. Retention: 7 years (Art 12/19-grade, cheap insurance regardless of risk tier). Exposed as a read-only governance API (change feed + current inventory of prompts/tools/versions) so enterprise AI-governance platforms (ServiceNow-style control towers) can subscribe rather than drift.

## Human-in-the-loop design

HITL is a durable async queue, never a modal dialog: a blocked improvement branch parks as a persisted Temporal workflow (survives restarts, waits days) with a typed request — CredentialGrant, DataAccessScope, MetricClarification, RiskyChangeSignoff, ObjectiveDisambiguation — while serving continues on the unmodified manifest. Approval tiers mirror change tiers: Tier 0 log-only (no human); Tier 1 no pre-approval but post-hoc weekly digest review; Tier 2 single approver via queue with 72h SLA, then escalation, then expiry (expired proposals are auto-rejected and archived, never silently applied); Tier 3 maker-checker dual control — proposer identity ≠ approver, two humans from distinct CODEOWNERS groups, enforced by branch protection. Human attention is budgeted like a scarce resource (the inverted-U finding): a declared reviewer-capacity budget per week, low-urgency proposals batched into digests, and load-aware routing — but load pressure NEVER auto-approves (that recreates Replit); it only delays. Anti-rubber-stamping design: approval UI shows evidence + diff + an auto-generated 'what could go wrong' section, and requires an active input (select a failure mode considered, or answer a one-line check question) rather than one Approve button; approve-rate >95% combined with median decision time <10s fires a rubber-stamping alarm that is itself an audited metric. Ambiguous objectives ('maximize revenue' — over what horizon, which segment, margin guardrails?) are first-class ObjectiveDisambiguation requests captured at objective-definition time together with 5–10 golden decision cases co-authored with the business owner — the loop is forbidden from resolving metric ambiguity by optimizing whatever is measurable. Credentials and data-access grants are HITL by construction: the agent has no path to mint access, only to file a request that blocks that branch.

## Novel variations

- TWO-SIDED ERROR BUDGET GOVERNING GATE WIDTH (the anti-frozen-loop mechanism): the improvement loop carries SLOs in both directions. A regression budget (e.g., max 2 user-visible regressions from auto-applied changes per quarter) that, when consumed, automatically demotes change types one tier (Tier 1 -> Tier 2, requiring humans again); and an improvement-velocity SLO (e.g., >= N accepted improvements/month, staleness alarms on the Ledger backlog) whose sustained health plus 90 days of zero regressions for a given change type auto-generates a PROMOTION PROPOSAL to move that type down a tier — reviewed by humans, evidenced by the type's survival statistics from the Audit Chain. Gate width becomes a data-driven control loop instead of a permanent political setting; this is Palantir's trust ladder made mechanical.
- ROLLBACK REHEARSAL AS A PROMOTION GATE (the 3am drill): no manifest may reach the canary label until the Deployment Controller has demonstrated, in staging, a full automated rollback of that exact manifest to its predecessor in under 60 seconds — including memory/index state (see next item) and prompt-cache invalidation. The rehearsal result is recorded in the ImprovementRecord. This converts 'rollback works' from an assumption discovered false during an incident (Replit: the agent falsely claimed rollback was impossible) into a continuously-verified invariant. Corollary: every improvement ships with its own auto-generated rollback runbook and 2-3 self-targeted canary probes — a change that cannot describe how to detect and undo itself is rejected at S1.
- MANIFEST-ATOMIC MEMORY VIA COPY-ON-WRITE KNOWLEDGE BRANCHES: the known killer of config rollback is state contamination — playbook entries, memory consolidations, and vector-index writes are not reverted by repointing a label. GateKit therefore snapshots the entire knowledge substrate (playbook, skill library, vector indexes, semantic model) as lakeFS/DVC-style branches, and the Harness Manifest pins a knowledge-branch ref exactly like a prompt version. Improvements that write memory do so on a fork; promotion merges the fork ref into the manifest; rollback repoints to the prior branch ref. One label move reverts EVERYTHING the change touched, atomically.
- METERED PRIVATE-SET LEAKAGE BUDGET: adaptive-data-analysis leakage (every accept/reject bit leaks information; enough proposals make the private set effectively public) is treated as an operational quantity like an error budget — each private-slice query decrements a per-slice budget derived from Ladder-style noise thresholds; the Gatehouse dashboard shows remaining budget; exhaustion automatically triggers slice rotation from freshly labeled production traffic and invalidates in-flight proposals evaluated against the retiring slice. Leakage stops being a vague academic worry and becomes a paged-on metric with a runbook.
- TRIPWIRE PROBES + LINEAGE QUARANTINE: honeypot eval questions engineered so the superficially plausible answer is wrong and only actual data execution reveals the truth (planted sign-flips, discontinued products, NULL-poisoned cohorts). A proposal improving the public score while failing tripwires is not merely rejected — its entire proposal lineage (same limitation diagnosis, same seam) is quarantined for a cooling-off period and flagged for human audit, and the event increments the first-class reward-hacking-rate metric. This punishes hacking at the lineage level where it actually propagates, not per-proposal where retries are free.
- CMP-LITE SCHEDULING (spend improvement budget where lineages pay off): the bandit that selects which limitation to attack next is weighted by 30-day production survival of past fixes per limitation-type (Huxley-Godel clade-productivity, simplified to a per-type survival rate), not by immediate eval delta — directly countering the measured weak correlation between a change's benchmark score and its lineage's downstream value, and starving limitation-types whose fixes keep getting rolled back.

## Risks

- Approval-queue starvation silently freezes the loop: blocked Tier 2/3 branches accumulate if reviewers do not clear the queue. Mitigation: queue-age SLAs with escalation, expiry semantics, velocity SLO alarms — but if the org will not staff reviewing, the system degrades to Tier 0/1 improvements only, and that must be an explicit, visible state, not a surprise.
- Private-set depletion and distribution mismatch: rotation requires a steady supply of freshly labeled questions with verified answers — the scarcest, most expensive asset in the whole design. If labeling lags, either the leakage budget halts private gating (loop stalls) or discipline slips (Regimes' +0.01 over-promotion split shows lax gates destroy gains).
- Sandbox-to-prod fidelity gap: changes green on lakeFS snapshots can break on live data distributions, live permissions, and live schema states; snapshotting enterprise data into eval environments also creates its own PII/governance problem requiring masking pipelines that can themselves distort evals.
- Residual reward hacking is the steady state, not zero (63%->34% is the best published trajectory): if the weekly human audit sample is skipped under time pressure, hacked improvements accumulate compound interest. The audit sample must be budgeted headcount, not volunteer virtue.
- Envelope creep / identity drift: successive small in-envelope changes compose into behavior no single change review anticipated (the EU AI Act 'identity problem'). Mitigation: quarterly re-baselining against the second-order reserve and against the original conformity envelope — an expensive ritual that will be politically tempting to skip.
- Judge decay and self-preference contamination: the frozen different-family judge drifts from human judgment as question distributions shift; silent judge-model deprecations force re-pinning. Quarterly kappa recalibration against fresh human labels is load-bearing and must be on-call-owned.
- Cost blowout in shadow/eval: shadow mode is ~2x inference spend; staged gates plus multi-instance SQL execution against replicas have real warehouse cost. Fixed per-eval dollar caps protect against runaway candidates but also cap how thoroughly borderline changes are examined.
- Two-sided error budget gaming: if regressions are under-detected (weak canary probes), the trust ladder auto-widens on false evidence — the promotion path is only as trustworthy as the regression detectors, so probe quality needs its own review.
- Rollback blind spots outside the manifest: external side effects (cached results in downstream BI dashboards, emails already sent, tickets filed) are not reverted by label repoint; anything side-effectful must stay behind staging-only or human-approved execution.
- Organizational: rubber-stamping alarms and reviewer-capacity budgets accuse humans of doing their jobs badly — expect political pressure to disable exactly the metrics that keep the HITL layer honest.

## MVP scope

BUILD FIRST (12-week MVP, in order): (1) Baseline IAR with Router + NL->SQL over a governed semantic layer (dbt MetricFlow or Wren MDL) + one RAG leg, all as DSPy modules, all data access via read-only scoped MCP tools with sqlglot AST validation and EXPLAIN cost gates. (2) Harness Manifest + label-based deploy/rollback (Langfuse prompt versions pinned by a manifest lockfile in Git; rollback = label repoint + cache invalidation), with the 3am rollback drill in CI from day one. (3) OTel GenAI tracing with manifest-hash on every span; ClickHouse + Grafana dashboards for cost/latency/error/hacking-rate. (4) Limitation Ledger with four detectors only: SQL execution failures, metric-gap fallbacks, schema-drift diff, thumbs-down. (5) Public golden set (~150 questions from real analyst traffic, frozen lakeFS snapshot) + CI regression gate with paired bootstrap; a small private slice (~50 questions) gated by a manually-operated Gatehouse. (6) Tier 0 improvements ONLY, and even those behind single-human approval for the first 30 days: verified-query additions, playbook deltas, few-shot examples. (7) Hash-chained audit log + Temporal approval queue with the typed request kinds. EXPLICITLY DEFER: GEPA prompt evolution (phase 2, after the golden set stabilizes — it is a $2-10/run drop-in once gates exist); MCP tool minting from trajectories (phase 3); trust-ladder auto-promotion (needs 90 days of survival data before the mechanism has anything to act on); leakage-budget automation (manual rotation is fine at MVP proposal volume); multi-objective heterogeneous eval suites (phase 2); counterfactual/backtest decision scoring (phase 3, needs outcome-data plumbing); code-level self-modification (deferred indefinitely — the evidence says 10-100x cost for uninterpretable artifacts; revisit only with a dedicated offline experiment budget); L2 ignition (out of scope, published attempts failed — scope is L1 and say so in the docs). MVP success criterion: 10 accepted Tier 0 improvements with full audit records, zero silent regressions, one live-fire rollback executed in under 60 seconds by an on-call engineer who has never seen the change.

## Tech stack

Python 3.12. Serving/pipeline: DSPy for module structure (GEPA-ready), FastAPI service, MCP for all tool/data access (catalog-governed where the platform offers it, e.g. Databricks managed MCP / Unity Catalog). Durable workflows + HITL queue: Temporal (approvals survive restarts for days). Policy: OPA/Rego sidecar between agent and tools, policies in a repo the agent cannot write. Versioning/deploy: Git + GitHub Actions CI, Langfuse (self-hosted, data residency) for immutable prompt versions with environment labels; Harness Manifest as a lockfile; branch protection + CODEOWNERS for maker-checker. Observability: OpenTelemetry GenAI semantic conventions -> ClickHouse + Grafana (vendor-portable to Datadog/LangSmith). Audit: Postgres append-only event table with SHA-256 hash chaining, hourly anchoring to S3 Object Lock (WORM). Eval infrastructure: lakeFS for frozen warehouse-snapshot branches and copy-on-write knowledge branches; gVisor (k8s-native) sandboxes for candidate replay, Firecracker/E2B if agent-generated code is ever admitted; sqlglot for AST validation; scipy/statsmodels + a confidence-sequence library for bootstrap and mSPRT gates. Judging: pinned frozen judge from a different model family than the generator (e.g., generator on Claude, judge on a pinned GPT/Gemini version), kappa-calibrated quarterly. Warehouse legs: Snowflake/Databricks/Postgres read-only replicas with row-level security enforced in-database via session variables — never in the LLM. Boring, proven parts everywhere; the only custom-built components are the Gatehouse service, the Limitation Ledger, and the manifest/deploy controller glue.
