# FORGE: A Capability-Maximal, Governable Self-Improving Harness for Enterprise Insights Agents

> Design lens: **capability-first**. An AI-research lens that maximizes the self-improvement ceiling while staying governable.
>
> One of four independent design proposals generated during the design program. The synthesized architecture in `docs/` merges the winning proposal with grafts from the other three.

## Thesis

The bet: the vast majority of achievable gain in enterprise insights agents comes from harness engineering (Spider 2.0 went 10%→70-97% in 18 months from scaffolds, not models), so we should give the improvement loop the *widest possible improvement surface* — memory, prompts, plans, retrieval configs, minted skills/tools, semantic-model artifacts, and (sandboxed) generated code — and make it governable not by shrinking the surface but by structural separation: the evaluator, audit ledger, and policy kernel live in a trust domain the improving system can never read or write. Capability comes from bi-level optimization with a lineage-productivity scheduler and an adversarial limitation-mining economy; governability comes from the fact that every artifact the loop touches is a versioned, diffable text/config object promoted through a public/private gated pipeline where ~90% rejection is the designed steady state.

## Architecture

Nine named components in three trust domains.

TRUST DOMAIN A — SERVING (the thing that improves):
1. **Conductor** — the baseline insights agent: a router/planner (LangGraph state machine) that decomposes a business question into sub-queries across three legs: SQL leg (semantic-layer-first: resolve to named governed metric via dbt MetricFlow/Cube; fall back to generated SQL via sqlglot-validated NL2SQL), Lake leg (federated planner over warehouse/lake connectors), and KB leg (hybrid BM25+dense retrieval with reranking, permission-trimmed per caller). Every stage is a DSPy module so it is GEPA-optimizable. All tool access goes through governed MCP tools with on-behalf-of-user auth.
2. **Substrate** — the mutable knowledge state: (a) ACE-style Playbook (structured delta items, dedup-merged, never monolithically rewritten); (b) Skill Vault (Voyager/Alita-G-style library of execution-verified, parameterized skills — SQL templates, join paths, metric resolvers — registered as MCP tools, embedding-indexed); (c) Memory Graph (Mem0-style ADD/UPDATE/DELETE/NOOP with tombstones and provenance, holding schema facts, metric definitions, source quirks); (d) Verified Query Repository (human-approved question→SQL pairs).
3. **Harness Manifest** — a Git-versioned lockfile pinning every prompt version, tool version, retrieval config, plan template, model ID, and Substrate snapshot hash. The running agent is always reconstructible from one commit hash; rollback = repoint one label.

TRUST DOMAIN B — IMPROVEMENT (the outer loop, hand-tuned and frozen):
4. **Prospector** — limitation miner over the Trace Lake (all OTel GenAI spans). Runs as sleep-time compute (Letta pattern), off the serving path.
5. **Examiner** — adversarial question-generation agent that red-teams the Conductor (detail in limitation_detection).
6. **Foundry** — the improvement proposer: a fixed, hand-tuned improver agent with a library of typed improvement operators (one per surface tier). It reads Prospector dossiers, drafts a change as a PR against the Manifest repo with evidence attached. The Foundry's own prompts are human-maintained; only its *playbook* (ACE deltas about what kinds of improvements work here) may self-update — our bounded ignition experiment.
7. **Ledger-Scheduler** — HGM-inspired bandit that allocates the improvement budget across limitation lineages by estimated Clade-Metaproductivity, not immediate eval delta.

TRUST DOMAIN C — CONTROL (never writable, never readable-in-full, by Domains A/B):
8. **Gatekeeper** — the evaluation service: holds the private golden sets, runs the staged gate cascade in Firecracker/E2B sandboxes against frozen data snapshots, reports only Ladder-style thresholded accept/reject to the Foundry. Uses a frozen different-model-family judge.
9. **Chronicle + Policy Kernel + Concierge** — Chronicle: append-only SHA-256 hash-chained event log (event-sourced, externally anchored, running outside the agents' privilege boundary — the DGM log-fabrication lesson). Policy Kernel: OPA/Rego engine classifying every proposed change and every tool call as allow/require_approval/deny; the policy repo is outside the agent's writable scope. Concierge: the durable HITL queue (Temporal signals / LangGraph interrupt + checkpointer) with capacity-budgeted escalation.

Connections: Conductor emits traces → Trace Lake → Prospector/Examiner mine limitations → Ledger-Scheduler picks one → Foundry drafts a Manifest PR → Policy Kernel classifies → Gatekeeper cascade scores → (Concierge if approval needed) → merge repoints the staging label → shadow mode → production label. Every arrow is a Chronicle event.

## Improvement surface (what the system may modify about itself)

Five tiers, each a declared "pre-determined change class" (EU AI Act Art 43(4) envelope), each with its own gate depth and approval class. The tier IS the Rego classification key.

**T0 — Memory & lessons (standard change, auto-apply with logging):** Reflexion-style failure lessons; Playbook delta items (append/merge only, never rewrite); Mem0 ADD/UPDATE/NOOP on schema facts (DELETE requires T2 treatment — tombstone only); new golden-set candidate cases mined from failures.
**T1 — Prompts & tool descriptions (standard if within tested templates; normal otherwise):** GEPA-evolved prompts for any DSPy module (NL2SQL, router, query rewriter, synthesizer); tool descriptions; few-shot demo selection. Human-readable diffs by construction.
**T2 — Plans, routing, retrieval configs (normal change, async approval or auto after N clean shadow runs):** plan-template library additions (ADAS-style archive of pipeline compositions); router policy updates trained from logged which-source-answered-correctly outcomes; retrieval params (chunking, hybrid weights, reranker config); canary-query definitions; EXPLAIN cost-gate thresholds.
**T3 — Skills, tools, semantic artifacts (normal change with mandatory HITL for anything touching definitions or access):** minting parameterized skills from successful verified trajectories into the Skill Vault as MCP tools (new-tool admission = HITL gate, always — tool-poisoning surface); proposed Verified Queries (human approves, becomes trusted asset); proposed semantic-layer edits (new metric definitions, join relationships, synonyms — Snowflake's agentic semantic-model pattern generalized); proposed new golden decision cases.
**T4 — Generated code (high-risk, dual-control maker-checker, offline campaigns only):** new validators, rerankers, result-sanity checkers, connector shims — authored by the Foundry, executed only inside sandbox tiers, deployed only after two independent human approvals from distinct CODEOWNERS groups, with a complexity-tax gate (see evaluation). Full DGM-style scaffold evolution is reserved for quarterly offline "expedition" runs against snapshots, never the serving loop.

Explicitly NOT on the surface: model weights (SEAL's forgetting curves say no), the Policy Kernel, the Gatekeeper, the Chronicle, credentials/scopes (the agent can only *file requests*), and the Foundry's own code (only its playbook).

## Improvement loop

**TRIGGER.** Four trigger sources feed a unified Limitation Register (typed records: {class, evidence trace IDs, frequency, estimated business impact, blocked-on}): (1) Prospector's nightly sleep-time mining of the Trace Lake — clusters failed/low-scored episodes into limitation classes (failed SQL, empty retrievals, fallback-to-raw-SQL events, judge-flagged unsupported claims, user thumbs-down, clarification loops, EXPLAIN-gate rejections, schema-drift diffs from information_schema monitoring, canary regressions, freshness-gap alerts); (2) Examiner's adversarial probes; (3) hard signals from serving (exceptions, timeouts, policy denials); (4) human-filed limitations from analysts.

**SELECT.** Ledger-Scheduler runs a CMP bandit: each limitation lineage (a limitation and all improvement attempts descending from it) carries an escrowed dollar budget and a running estimate of downstream payoff. Selection weight = estimated clade productivity × business-impact prior ÷ recent spend. This replaces greedy pick-the-biggest-eval-delta, per the HGM Metaproductivity-Performance Mismatch evidence.

**PROPOSE.** Foundry instantiates the operator matching the limitation class (GEPA run for prompt-class, skill-mint for missing-tool-class, semantic-edit for metric-class, plan-template for decomposition-class...). Output is always a PR: Manifest diff + machine-readable change record {what, why, evidence trace IDs, expected effect, tier, blast radius}. One limitation → one change (DGM discipline). If the operator needs something it lacks (credentials, data grant, canonical metric definition), it files a typed Concierge request and the lineage parks as a durable checkpoint — serving continues on the unmodified harness.

**GATE (staged cascade, fixed dollar budget per candidate, rejection is cheap):**
G0 static: sqlglot AST checks, schema validation, policy classification, complexity tax computed, secret/scope-widening scan (hard fail). ~$0.
G1 sandbox: candidate manifest boots in a Firecracker microVM against frozen data snapshots; smoke suite of 10 tasks. 
G2 public eval: full public golden slice (the Foundry sees these scores and may iterate — its inner optimization signal).
G3 private eval: Gatekeeper runs the hidden slice + execution-grounded checks (multi-instance result-set comparison, numeric-claim reconciliation) + frozen other-family judge; paired bootstrap CI over questions; reports ONLY accept/reject at a noise-calibrated threshold (Ladder). Also scores the *second-order reserve*: whole business objectives never used in any loop, checked at release audits.
G4 approval: Rego verdict → auto-merge (T0/standard), Concierge async queue (normal), synchronous dual-control (T4/high-risk). Approval UI = evidence + diff + auto-generated "what could go wrong" + mandatory reason selection (anti-rubber-stamp).

**DEPLOY.** Merge repoints the *staging* Manifest label → shadow mode: candidate runs in parallel on live analyst queries (side-effect-free by construction — read-only credentials), independent judge compares paired outputs, mSPRT anytime-valid test monitors continuously. Promotion to the *production* label on threshold + zero policy violations; cache invalidation fired (LangSmith TTL lesson).

**MONITOR.** Post-promotion: canary queries hourly; reward-hacking-rate dashboard (sampled human audits of accepted changes); per-change attribution via trace→manifest-version links in every span; automatic rollback trigger = canary regression or hacking flag (emergency change, always allowed, logged). Outcomes as they mature (Brier ledger on the agent's probabilistic claims, backtest deltas) flow back into the lineage's CMP estimate — closing the scheduler loop.

## Limitation detection

Five concrete mechanisms, all producing typed Limitation Register entries with evidence trace IDs:

1. **Trace autopsy (Prospector, nightly sleep-time):** MLflow-3-style trajectory scorers localize *which stage* failed (retrieval hit-rate vs SQL validity vs synthesis groundedness) so improvements route to the right subsystem. Clustering over failure embeddings surfaces recurring classes; each cluster becomes one register entry with frequency and sample traces. Judge outputs are mapped to specific config recommendations (Databricks pattern) — machine-generated proposals with evidence pre-attached.
2. **Structural tripwires in the serving path:** every fallback-to-raw-SQL event = "metric missing from semantic layer" signal; every EXPLAIN cost-gate rejection = query-efficiency limitation; every clarify-instead-of-guess loop ≥2 turns = ambiguity limitation (routed to HITL as a metric-definition request, never resolved by the loop itself — the Goodhart-worst spot); every permission denial = access-gap record (blocked-on: credential grant).
3. **Drift sentinels:** information_schema diffed nightly against the semantic model and Skill Vault preconditions (column renames break skills); corpus freshness/coverage monitors comparing incoming question distribution against KB coverage; canary queries per source fired hourly with drift alerts. Skills carry *half-lives* and are re-certified by re-execution against live schema (see novel variations).
4. **Examiner adversarial mining:** an agent paid (in scheduler budget) to construct questions the Conductor fails — mutations of real analyst questions along known failure axes (NULL semantics, fan-out joins, timezone boundaries, ambiguous business nouns, cross-source entity joins), validated by executing the ground-truth answer itself. A confirmed kill = a new limitation + a new golden case. This actively generates the verification signal for *silent wrong answers*, the class user complaints never surface.
5. **Counterfactual gap probes:** for each business objective, the Prospector periodically asks "what data would materially change the top recommendation?" and checks whether the harness can access/compute it; unreachable-but-material data = a missing-access limitation filed to Concierge with a business-impact estimate. Also: "we cannot backtest this recommendation" is itself a detectable limitation triggering a request for outcome-data access or an experiment.

Anti-gaming rule: the limitation-detector's health metric is *coverage of independently-audited failures* (from human spot audits and Examiner kills), never "number of limitations reported" — so the system cannot look better by going blind.

## Evaluation design

Composite scoring with the AIDE² gate recipe as the spine, hardened for an insights domain where quality isn't unit-testable.

**Score composition (per candidate):** (a) execution-grounded correctness on golden questions — result-set comparison across multiple perturbed DB instances (test-suite accuracy; plain EX has ~9% FP / 17% FN), numeric-claim extraction from narrative insights reconciled against independently re-executed queries; (b) insight-recovery rate on InsightBench-style internal sets (experts curate 10-50 known insights per objective recoverable from frozen snapshots, two-level judge scoring); (c) frozen different-family LLM judge with fact-grounded rubric (groundedness, completeness, actionability), calibrated quarterly against 200+ human labels via Cohen's kappa, order-randomized, length-normalized; (d) SICA-style utility fold-in: score AND dollar cost AND p95 latency, under a fixed per-eval budget; (e) Brier ledger on probabilistic claims as outcomes mature (strictly proper — the one score the agent can only improve by being right).

**Anti-Goodhart architecture:** (1) PUBLIC/PRIVATE split — Foundry optimizes against the public slice; survival decided on the private slice held by the Gatekeeper in a separate trust domain, reported only as thresholded accept/reject (Ladder) to throttle leakage; private slices rotated monthly from fresh production traffic; a *second-order reserve* of entire objectives/domains touched only at quarterly release audits (Weco's second-order generalization test). (2) Heterogeneity — every candidate is evaluated across ≥3 business objectives and ≥2 data-source types simultaneously; single-objective wins don't merge. (3) Reward-hacking rate as a first-class dashboard metric: weekly human audit of a random sample of accepted changes; trace-level anomaly detection (hard-coded outputs, golden-answer caching, judge-pleasing surface features); expect nonzero steady state (Weco: 34% *after* defenses) and budget continuous audit sampling accordingly. (4) Statistics — paired bootstrap CIs (~1000 resamples over questions, multiple generations per item) for offline gates; mSPRT anytime-valid tests for shadow promotion so continuous peeking is legal; one designated primary metric per gate to avoid multiple-testing inflation. (5) **Complexity tax** — every diff pays a gate penalty proportional to added tokens/branches/dead-code-detector hits; a change must beat threshold *after* tax, directly pricing in the AIDE² uninterpretability failure. (6) The improver never judges its own work: generator and judge from different model families (Digits pattern); the Foundry cannot query the judge directly.

## Audit design

Two layers with different jobs: OTel traces for debugging, the Chronicle for auditors.

**Chronicle record schema (one hash-chained JSON event per state transition):** {event_id, prev_hash, sha256, timestamp, actor (agent identity via per-agent SPIFFE ID / human identity), event_type ∈ {limitation_registered, lineage_selected, proposal_opened, gate_result(G0..G4), approval_requested, approval_decision(approver, reason_code, latency), label_moved, shadow_started, promoted, rolled_back, memory_op(ADD/UPDATE/TOMBSTONE), skill_minted, skill_recertified/retired, escalation_filed, budget_spent}, payload: {manifest_commit_before/after, diff_ref, evidence: [trace_ids], eval: {public_scores, private_verdict, CI, p-value, cost}, policy: {rego_rule_id, verdict, tier}, blast_radius}}. Every accepted improvement thus answers what/why/evidence/approver in one queryable record — the brief's requirement 3 verbatim.

**Storage & integrity:** append-only event store (Postgres + periodic anchor of the chain head to WORM/object-lock storage), written by a logger process *outside the agents' privilege boundary* — agents cannot suppress or fabricate writes (the DGM fabricated-logs lesson). Event sourcing gives exact replay: "what did the harness contain and believe on date D" reconstructs from the fold of events, which is the incident-forensics story and the EU AI Act Art 12 story simultaneously.

**Versioning substrate:** the Manifest repo (Git) holds the diffs; Chronicle events reference commits; Langfuse-style immutable versions + movable environment labels give one-operation rollback; every serving span carries the manifest commit hash so any answer is attributable to an exact harness version. Memory writes are NOT reverted by config rollback — hence Mem0 ops are themselves Chronicle events with tombstones, replayable to undo. A governance API exposes the current tool/prompt/version inventory and the change feed for enterprise control towers (ServiceNow-style) to consume.

## Human-in-the-loop design

Humans are a metered, depletable resource (oversight-capacity evidence: realized safety is inverted-U in escalation rate) — so the design maximizes the auto-applied standard class and spends human attention only where it buys safety.

**Change-class routing (ITIL mapped to Rego verdicts):** STANDARD (T0, template-bounded T1): auto-apply after gates, log-only — humans see a weekly digest. NORMAL (T1 novel, T2, T3 skills/verified queries/semantic edits): async Concierge queue; durable checkpoint (Temporal signal / LangGraph interrupt + checkpointer) parks the lineage for hours/days across restarts while serving continues; SLA + escalation ladder + expiry semantics so queue starvation is visible, not silent. HIGH-RISK (T4 code, new data-source scopes, anything touching definitions of financially material metrics, any change to eval/policy adjacency): synchronous dual-control — maker ≠ checker, two approvers from distinct CODEOWNERS groups (data owner + platform owner), mitigating the kappa≈0.52 single-reviewer lottery. EMERGENCY (rollback): always allowed, retrospectively reviewed.

**Blocking requests (requirement 4):** typed Concierge request objects — credential_grant, data_access_grant, metric_definition_clarification, objective_clarification ("maximize revenue — over what horizon? which segment? margin floor?"), risky_change_signoff, experiment_authorization. Each blocks exactly its lineage branch; the agent structurally *cannot* mint its own access (credentials live outside its reach), so these are HITL by construction.

**Anti-fatigue engineering:** declared reviewer capacity budget with load-aware batching into digests; approval UI shows evidence + diff + auto-generated failure hypotheses and requires an active input (select a reason, answer one check question) rather than a bare Approve button — countering the explainability paradox where fluent rationales increase deference; approve-rate >95% with sub-10-second decisions fires a rubber-stamping alarm, itself a Chronicle metric; filler-flood detection (an improvement wave generating unusual escalation volume is treated as a possible fatigue attack and throttled).

## Novel variations

- LIMITATION BOUNTY ECONOMY: the Examiner agent is paid in scheduler budget for each *confirmed* novel failure (validated by executing ground truth itself), and each limitation lineage carries an escrowed dollar budget that improvement attempts bill against; lineages whose promoted changes keep paying off receive budget dividends (HGM clade-metaproductivity as an internal market). This turns limitation detection from passive log-mining into an adversarial economy that actively hunts the silent-wrong-answer class no user ever reports, and it gives the audit log a currency-denominated account of where improvement effort went and what it returned.
- SKILL HALF-LIVES WITH EXECUTION RE-CERTIFICATION: every minted skill/verified query carries a decay clock and declared preconditions (tables, columns, metric versions it depends on); the nightly drift sentinel re-executes a cheap certification probe for skills whose preconditions changed or whose half-life expired; failures demote the skill to 'stale' (retrieval-suppressed, Chronicle event) rather than deleting it. This solves the two documented library failure modes at once — Voyager-style bloat/near-duplicates and schema-drift-encoded hacks — and makes the Skill Vault self-pruning without an LLM rewriting anything.
- COMPLEXITY TAX + INTERPRETABILITY GATE TERM: candidates are charged a gate penalty computed from diff size, added control-flow branches, dead-code-detector hits, and a small-model 'explainability probe' (can a cheap model correctly summarize what the diff does? — measured agreement with the Foundry's stated intent). A change must beat the acceptance threshold after tax. This directly prices the AIDE²/DGM uninterpretable-evolved-code failure into the fitness function instead of hoping reviewers catch it, and biases the search toward the prompt/playbook/skill end of the surface where audit is cheap.
- LADDER-THROTTLED ACCEPT/REJECT-ONLY PRIVATE SCORES: the Gatekeeper never reports numeric private scores to the improvement domain — only accept/reject at a noise-calibrated step threshold (Blum-Hardt Ladder), with monthly rotation of private slices from fresh traffic and a quarterly-only second-order reserve of whole untouched objectives. Adaptive-data-analysis leakage (every bit of feedback slowly makes the holdout public) is the quiet killer of public/private splits; thresholded reporting is the cheapest published mitigation and nobody builds it by default.
- BOUNDED IGNITION VIA IMPROVER PLAYBOOK: full L2 (evolved improver) failed in AIDE² and is out of scope, but we run a constrained variant — the Foundry's code and prompts are frozen and human-owned, while an ACE-style 'improver playbook' (what operator worked for what limitation class in THIS enterprise, with evidence) accumulates as gated T0 deltas. This captures most of the plausible meta-learning gain (operator selection and diagnosis quality) with none of the ungovernability of self-modifying improver code, and the playbook is a human-readable audit artifact.
- COUNTERFACTUAL REPLAY DIVIDEND: every promoted change is retro-scored by replaying the previous N days of real production questions through both old and new manifests in the sandbox (paired, order-randomized judging + execution grounding); the measured 'would-have-been' delta is appended to the change's Chronicle record. This converts vague 'the eval said it was better' into workload-denominated evidence for auditors, feeds the CMP estimate with real-distribution signal, and catches golden-set overfitting within days of promotion.
- AMBIGUITY LEDGER AS FIRST-CLASS ARTIFACT: contested business nouns ('revenue', 'active user', 'churn') are typed records with candidate definitions, owning teams, and resolution status; the Conductor consults the ledger before answering, answers under an explicitly named definition when resolved, and files a Concierge clarification when contested. Detection is automated: the Prospector flags when two answers for the same metric term used different SQL lineages. This routes the single most Goodhart-dangerous limitation class (ambiguous metrics) permanently to humans while making disambiguation itself an auditable, improving asset.

## Risks

- Reward hacking is the steady state, not an anomaly: even with the public/private split, expect residual gaming (Weco: 34% after defenses). Mitigation is budgeted continuous human audit sampling and execution-grounding of every numeric claim — if audit budget is cut, the hacking-rate metric silently decays into fiction.
- Holdout depletion: every accept/reject bit leaks; with a ~90% rejection rate the private set is effectively public after hundreds of proposals. Rotation from fresh traffic is mandatory OPEX, and one engineer with read access to the private slice destroys the guarantee — treat Gatekeeper access as a formal insider-threat surface.
- Envelope creep / identity drift: successive in-envelope changes compose into out-of-envelope behavior (no single change is 'substantial' but the aggregate is). Mitigation: quarterly re-baselining audits against the original assessment using the second-order reserve; without them the EU AI Act pre-determined-changes posture quietly becomes false.
- Approval-fatigue exploitation: the loop itself can (emergently) flood reviewers with filler escalations before a risky change; capacity-aware throttling that auto-approves under load recreates the Replit incident. The rubber-stamping alarm and filler-flood detector must be non-disableable.
- Sandbox-to-prod fidelity gap: changes that pass on frozen snapshots break on live permission structures and data distributions; snapshotting enterprise data into sandboxes also creates its own PII-governance problem. Mitigate with synthetic-plus-masked replicas and shadow mode as the real gate.
- Memory contamination outlives rollback: config rollback does not undo Substrate writes; a wrong 'fact' learned from a bad promotion persists. Every memory op must be an event with tombstones and replayable undo, and this is easy to under-build.
- Cost blowout: shadow mode ~2x inference, private evals across ≥3 objectives, replay dividends, and Examiner probes are all metered spend; DGM-class T4 campaigns cost $10k+. The fixed-budget-per-eval and lineage escrow discipline must be enforced by the Gatekeeper, not by convention.
- Complexity tax miscalibration: too high and the loop converges to trivial T0 tweaks (capability ceiling); too low and evolved artifacts drift toward uninterpretability. Needs its own quarterly human calibration.
- Judge ecosystem capture: if the frozen judge's model family is ever unified with the generator's (procurement decisions, model deprecations), self-preference bias silently corrupts every gate — pin and monitor judge lineage as a governance invariant.
- The scheduler can starve genuinely important but hard limitations (low early CMP) — pair the bandit with a business-impact floor so high-impact register entries cannot age out unworked without an explicit human decision.

## MVP scope

BUILD FIRST (12-16 weeks, one team): (1) Conductor baseline on LangGraph + DSPy modules with semantic-layer-first SQL leg and hybrid-RAG KB leg, all traffic emitting OTel GenAI spans into the Trace Lake; (2) Manifest repo + label-based versioning + one-operation rollback; (3) Chronicle hash-chained event log with the full record schema (cheap now, impossible to retrofit); (4) Gatekeeper v1: 300-500-question golden set built from real analyst questions with execution-grounded scoring, public/private split with accept/reject-only reporting, paired bootstrap gate; (5) improvement surface T0+T1 only — Reflexion lessons, ACE playbook deltas, Mem0 memory ops, verified-query proposals, nightly GEPA prompt-evolution runs ($2-10 each — economically trivial); (6) Concierge async queue with the typed request objects and the ambiguity ledger; (7) Prospector v1 (trace clustering + structural tripwires + schema-drift sentinel) and hourly canaries; (8) shadow-mode promotion with mSPRT.

EXPLICITLY DEFER: T4 code generation (quarterly offline expedition experiments only, after 6 months of gate telemetry); the Examiner bounty economy (needs a stable golden pipeline first — ship as experiment 2); CMP scheduler (start with impact×frequency priority, add the bandit once ≥50 lineages exist); counterfactual/uplift outcome linkage (needs propensity logging to accumulate); bounded-ignition improver playbook (after the Foundry's operator library stabilizes); multi-instance test-suite SQL evaluation (start single-snapshot + judge fallback); EU AI Act conformity documentation beyond the envelope declaration and Art-12-grade logging (which we get free from the Chronicle).

FEASIBILITY EXPERIMENT SEQUENCE: E1 — does the T0/T1 loop beat a static harness on the private slice over 4 weeks of nightly cycles (primary metric: private-slice insight-recovery + SQL execution accuracy, paired)? E2 — Examiner vs passive mining: marginal confirmed-failure yield per dollar. E3 — skill-minting ROI: token cost and accuracy delta of Vault retrieval vs regeneration. E4 — gate discipline ablation on a sacrificial branch: measure over-promotion when the private gate is weakened (expect the Regimes +0.01 effect — this is the governance sales artifact). E5 — one T4 expedition against snapshots with dual-control review, measuring complexity-tax behavior.

## Tech stack

Python 3.12. Serving/orchestration: LangGraph (state machine + interrupt/checkpointer) with Temporal for durable HITL branches; DSPy for all optimizable modules with GEPA as the prompt-evolution engine. Data legs: dbt MetricFlow or Cube (governed metric layer, MCP-exposed), sqlglot (AST validation), warehouse connectors via governed MCP servers with on-behalf-of-user auth (Databricks Unity Catalog managed MCP or equivalent); hybrid retrieval on the enterprise's existing vector store + BM25 with a reranker. Models: frontier model (Claude-class) for Conductor/Foundry; a different-family frozen judge (pinned version) for the Gatekeeper; cheap models for Examiner mutation and explainability probes. Policy: OPA/Rego sidecar, policy repo outside agent write scope. Sandboxing: E2B or Firecracker microVMs for candidate evaluation and any generated code; read-only, row/column-scoped DB credentials per source; egress allowlists. Observability: OpenTelemetry GenAI semconv → Langfuse (self-hostable, immutable prompt versions + movable labels) and/or LangSmith; Chronicle = Postgres append-only event store with SHA-256 chaining, head anchored to S3 Object Lock (WORM). Versioning/CI: Git + GitHub PR flow (branch protection, CODEOWNERS dual-control for T4), CI runs the G0-G2 gates on every manifest PR. Stats: scipy/statsmodels bootstrap, an mSPRT/confidence-sequence library (e.g., Eppo-style GAVI implementation) for shadow gates. Memory: Mem0-style consolidation over Postgres/pgvector with provenance columns and tombstones.
