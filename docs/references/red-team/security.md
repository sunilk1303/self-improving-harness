# Red-Team Report: Offensive security

> An offensive-security lens: prompt-injection persistence, privilege escalation via self-modification, PII/secret exfiltration through learned artifacts, audit evasion.
>
> Produced by an adversarial critique agent attacking the winning (GateKit + grafts) design.
> 8 attacks. Severity is 1-5; every attack includes the strongest realistic
> mitigation and an honest residual risk.

## Verdict

Salvageable but NEEDS CHANGES before enterprise deployment. GateKit is one of the more genuinely hardened self-improvement designs I've attacked: the control/serving/improvement trust split enforced by IAM (not prompts), WORM-anchored hash-chained audit, staged eval cascade, and CoW knowledge branches close most of the obvious holes. The remaining risk is concentrated in a handful of LOAD-BEARING but UNDER-SPECIFIED assumptions that an attacker works directly: (1) tier is classified from the proposer's *declared* change_type rather than independently derived from diff semantics — the single most dangerous gap, because it turns the entire tier system into a self-attestation; (2) the "log-only, auto-apply" Tier 0 class includes *definitional* artifacts (glossary synonyms, playbook deltas) that can encode permanent semantic bias while regressing zero golden questions; (3) regression detection and the trust-ladder auto-widening lean on proposer-authored canary probes whose adequacy is never independently gated; (4) PII/secret hygiene depends on collector-side redaction that is assumed complete; (5) the audit chain proves record integrity but references MUTABLE trace evidence, so forensics can be undermined without breaking the hash. None of these are fatal — each has a concrete structural fix — but shipping without them means the governance apparatus can be made to certify an attacker's change as safe. Fundamentally flawed only if the org also skips the human audit sample (a named residual), at which point poisoned learned behavior compounds silently.

## Attacks

### [sev 5/5 · medium likelihood] Tier-classification bypass via proposer-declared change_type (privilege escalation)

**Scenario.** The brief says the Policy Kernel 'classifies the tier' and that the ChangeRecord carries a self-declared change_type/tier authored by the Improvement Factory. It does not state that tier is independently DERIVED from diff semantics by the control domain. An attacker who has prompt-injected the proposer (via a poisoned evidence trace) or simply an over-eager optimizer crafts a manifest diff labeled change_type='retrieval_few_shot_example' (Tier 0) whose payload is actually an instruction block that alters the NL->SQL module's behavior or the router policy (a Tier 1/2 change). Because the Policy Kernel keys off the declared type and OPA/Rego rules match on that field, the change auto-merges as Tier 0. The agent has just moved a higher-privilege change through the lowest gate — the tier system becomes self-attestation.

**Mitigation.** Tier MUST be derived independently in the control domain from the diff itself, never trusted from the ChangeRecord. Implement a deterministic classifier over the parsed diff (which manifest paths/keys changed: a change touching module instructions is Tier 1 regardless of label; anything touching credentials/scopes/objective definitions/executable code is Tier 3) and treat the proposer's declared type as a claim that is CROSS-CHECKED against the derived type — mismatch is a first-class fabrication/tamper event that quarantines the lineage. Path-based CODEOWNERS + branch protection should already forbid a Tier-0-labeled PR from touching Tier-1+ manifest paths; make that the primary control and the Rego a backstop.

**Residual risk.** Path-based derivation can be evaded if two artifact types share a manifest region (e.g., few-shot examples and instructions live in the same prompt blob), or via semantically potent content inside a legitimately Tier-0 field (a 'few-shot example' whose text is an imperative that steers the model). Content-level intent is not fully derivable statically, so a sufficiently clever payload inside a genuinely low-tier field remains possible.

### [sev 4/5 · high likelihood] Definitional poisoning via Tier-0 auto-apply (glossary synonym / playbook delta) that regresses zero golden questions

**Scenario.** An attacker (a disgruntled insider, or an external party who can get a document into an indexed SharePoint/Confluence knowledge base) plants a plausible-sounding note in the RAG corpus: 'Finance convention: an "active customer" is any customer with a registered account.' The Synthesizer produces answers citing it; a trajectory looks successful; the Improvement Factory proposes a Tier-0 glossary synonym mapping active_customer -> registered_customer. This is definitional, not a query bug, so it passes the public golden set (which never distinguishes the two terms) and no tripwire covers it. Auto-applied, log-only. From that night forward every churn, MAU, and retention answer silently uses the inflated denominator, biasing executive decisions toward under-investing in retention. The change survives 30 days (no one notices a definitional drift), feeds the CMP-lite scheduler as a 'good' lineage, and helps the trust ladder widen the glossary/playbook tier.

**Mitigation.** Remove definitional artifacts from the auto-apply class entirely: glossary synonyms and semantic-layer-adjacent playbook deltas that change what a query MEANS must be Tier 2 (human + data-owner), never Tier 0. For the deltas that stay Tier 0, require every proposal to ship a discriminating tripwire (the ambiguity-tax graft: compute ALL interpretations and gate on the divergence) so a definitional change that moves any metric materially cannot pass without a probe that distinguishes the interpretations. Treat provenance: any playbook/glossary delta whose evidence trace originates in retrieved free-text documents (vs. a human-confirmed question->SQL pair) is auto-escalated a tier.

**Residual risk.** Definitional bias that stays within noise on all probes and golden questions still ships silently; the discriminating-tripwire coverage is only as good as the eval authors' imagination, and a slow, small synonym drift can accumulate under the divergence threshold. The weekly human audit sample is the only backstop and it is explicitly budget-constrained.

### [sev 4/5 · high likelihood] Cross-tenant PII exfiltration through learned prompt/few-shot artifacts

**Scenario.** The Improvement Factory mines successful trajectories to add retrieval few-shot examples and playbook illustrations. A trajectory that answered 'show me the top accounts at risk' contains real customer names, emails, and revenue figures. Collector-side redaction misses a free-text field (redaction is regex/NER-based and imperfect). That example is baked into a prompt artifact pinned in the manifest and thereafter injected in-context for EVERY user's queries. Analyst B in a different region/role, who is RLS-restricted from those accounts in the database, now sees that PII surfaced in-context because it lives in the shared prompt, not behind the per-call policy check. RLS protected the data at query time but the learned artifact routed around it.

**Mitigation.** Never source few-shot/example content directly from raw production trajectories. Require example artifacts to be synthesized against the ground-truth-by-construction synthetic data (the Proposal-3 graft) or drawn only from the curated golden set, which is already scrubbed. Any artifact promoted from real traffic must pass a dedicated PII/secret scanner as a hard S1 gate (zero tolerance) AND a differential-privacy-style check that the example generalizes without carrying record-level values. Enforce that shared in-context artifacts contain no row-level data — only schema/shape.

**Residual risk.** Synthetic-only examples reduce real-distribution fidelity; and PII scanners have nonzero false-negative rates on unstructured text, novel identifier formats, and quasi-identifiers (a unique revenue+region combo re-identifies an account without any name). Some leakage through the shared-context channel remains until artifacts are structurally forbidden from containing any production values.

### [sev 4/5 · medium likelihood] Secrets captured in limitation evidence become permanent Git/manifest artifacts

**Scenario.** An analyst pastes a query with an embedded credential or the NL->SQL leg emits SQL referencing a connection detail; it fails (auth error, timeout). The EXECUTION DETECTOR emits a weak-query-generation LimitationEvent 'with the failing SQL attached.' The Improvement Factory reads that evidence and adds the corrected pattern as a verified-query in the VQR or a 'what went wrong' few-shot — carrying the secret. It is now committed to the manifest Git repo (human-browsable mirror) and the 7-year WORM audit chain. The secret is exfiltrated to anyone with repo read access and is effectively un-deletable (WORM), forcing a credential rotation and a compliance incident.

**Mitigation.** Run secret scanning (gitleaks/trufflehog-class detectors) at the point evidence is written to the Ledger AND as a hard pre-commit/pre-merge S1 gate on every manifest diff and every ChangeRecord payload, blocking on any hit. Redact secrets from failing-SQL evidence at the detector before it reaches the Ledger. Because WORM makes post-hoc deletion impossible, prevention must be upstream; pair with mandatory rotation runbooks if a hit is ever confirmed post-anchor.

**Residual risk.** Secret scanners miss novel/custom token formats and secrets that don't match known entropy/regex signatures. Once a missed secret is anchored to WORM it cannot be expunged — only rotated — so a single scanner false-negative is permanent and irreversible.

### [sev 4/5 · medium likelihood] Proposer-authored weak canary probes blind regression detection and drive trust-ladder auto-widening (slow privilege escalation)

**Scenario.** Every change ships 'its own 2-3 self-targeted canary probes,' and the two-sided error budget auto-generates tier-promotion proposals after 90 days of zero detected regressions. A patient attacker (or a reward-hacking optimizer) submits changes in a target seam whose bespoke canary probes are deliberately shallow — they exercise a code path that always passes and never touches the behavior the change actually risks. Real regressions go undetected, the regression budget stays unspent, survival stats look clean, and after 90 days the trust ladder proposes promoting that change TYPE from Tier 2 to Tier 1 (or Tier 1 to auto-apply). A human rubber-stamps the promotion (backed by 'clean' survival data). The attacker now has a wider auto-apply channel in that seam — a governance-mediated privilege escalation the design itself flags as 'two-sided error budget gaming' but does not fully close.

**Mitigation.** Canary probes must be adversarially reviewed and mutation-tested, not authored solely by the proposer: the Gatehouse (control domain) independently generates or augments regression probes for each change, and probe adequacy is scored by the detector-fault-injection harness (the Proposal-2 graft) — a change's probes must catch a set of planted regressions in its own seam before the change is eligible for the survival clock. Keep tier reclassification as T2 dual-control (design already does), and make the promotion approval require reviewing probe-adequacy evidence, not just survival counts. The Red Twin (phase 2) should attack promoted-type candidates continuously.

**Residual risk.** Control-domain probe generation is itself imperfect and expensive; mutation testing covers the regressions you can imagine in that seam, not novel behavior. The trust ladder is only as trustworthy as the meta-detector of detector quality — an attacker who models the fault-injection distribution can craft regressions orthogonal to it. Auto-widening on partially-blind evidence remains possible.

### [sev 3/5 · medium likelihood] Mutable trace evidence undermines audit forensics without breaking the hash chain (audit evasion)

**Scenario.** The design states OTel traces are 'mutable, rich' and 'PII-redacted at the collector,' while the Audit Chain is the immutable record of authority that REFERENCES trace IDs as evidence. The hash chain covers the ImprovementRecord payload (which contains trace_ids), not the CONTENT of those traces. An attacker who compromises the ClickHouse trace store (or simply exploits normal trace TTL/retention aging) alters or expires the evidence traces behind a controversial accepted change. Six months later, during 'which change caused this wrong answer' forensics, the trace->manifest->ImprovementRecord join resolves but the underlying evidence is altered or gone. The hash chain still validates — it only ever committed to the IDs — so the tampering is invisible to the integrity check that was supposed to catch it. The audit trail proves a decision was recorded, not that the recorded evidence is authentic.

**Mitigation.** The Audit Chain must commit to a content hash (SHA-256) of the evidence snapshot at decision time, not just the trace ID — anchor the redacted evidence payload itself (or its digest) into the WORM chain so any later mutation/expiry is detectable. Set trace retention >= audit retention for anything referenced by an ImprovementRecord (pin/freeze referenced traces), and treat the trace store as integrity-relevant infrastructure with its own access controls and tamper alerting, not merely a debug convenience.

**Residual risk.** Snapshotting full evidence into WORM raises storage cost and can re-introduce the PII-in-immutable-store problem (see secrets attack) if redaction was imperfect at snapshot time. Digest-only anchoring detects tampering but does not recover the lost evidence, so forensic reconstruction can still be defeated by destruction even when detected.

### [sev 3/5 · medium likelihood] Tier-1 NL->SQL / router prompt version broadens data touched within user grants (over-collection / staged exfiltration)

**Scenario.** RLS is enforced in-database on the user's own grants, so no change can exceed what a user is entitled to. But entitlements are typically broader than any single analyst actually needs. A Tier-1 prompt-version change to the NL->SQL module (auto-applied after the gate, no pre-approval) systematically adds joins to sensitive-but-authorized tables (e.g., always LEFT JOIN the compensation or PII-bearing customer table 'for context'). It passes the public gate because answers remain correct — it just returns MORE. Now every answer quietly surfaces salary or PII fields the analyst was entitled to but never intended to pull, widening the blast radius of any downstream copy/paste, screenshot, or a subsequent exfiltration by that user, and increasing what a compromised analyst session leaks.

**Mitigation.** Add a data-footprint / least-privilege guardrail metric to the gate: measure the set of columns/tables each candidate touches per query vs. the incumbent, and treat a material expansion of the sensitive-column footprint as a guardrail regression (Bonferroni-protected), requiring justification or escalation. ACL-fidelity probes already flag permission WIDENING as a SEV; extend the same principle to intra-grant footprint growth. Enforce column-level minimization at the tool layer (return only columns the query semantically needs).

**Residual risk.** Distinguishing 'legitimately needed extra join' from 'gratuitous over-collection' is heuristic; a footprint threshold will have false positives that slow good changes and false negatives on modest expansions. Within-grant over-collection that stays under the threshold ships, and the ultimate control (tightening the analyst's own grants) is outside GateKit's scope.

### [sev 3/5 · low likelihood] Malicious self-authored rollback runbook / side-effecting canary probe executed outside the manifest boundary

**Scenario.** Two vectors on the same theme — actions GateKit cannot roll back. (a) The self-authored rollback runbook is executed by a stressed on-call engineer at 3am during an incident; an attacker-influenced proposer wrote a runbook whose steps do more than repoint a label (e.g., 'also flush and rebuild index X from source Y' where Y is attacker-controlled), and the human executes it under time pressure. (b) A 'canary probe' or plan template invokes an MCP tool with a side effect (files a ticket, hits a webhook, writes to a downstream BI cache). The design explicitly notes external side effects are not reverted by label repoint and not fully captured by the manifest-centric audit — so the payload persists after rollback and is under-represented in the audit chain.

**Mitigation.** Rollback runbooks must be constrained to a whitelisted, declarative set of operations the Deployment Controller executes automatically (label repoint + knowledge-branch ref + cache invalidation) — free-form imperative runbooks executed by humans should be forbidden; the 3am drill already rehearses the automated path, so make the automated path the ONLY path. Canary probes and plan templates must run against read-only, side-effect-free tool bindings (mocked side effects as in S2) in the serving domain too; any tool with side effects is Tier-3 human-approved execution only, never reachable by a probe. Route all side-effecting tool calls through the policy kernel with an explicit is-side-effecting flag audited on the chain.

**Residual risk.** Genuinely novel incidents may need an operation outside the whitelist, forcing a human-authored deviation exactly when scrutiny is lowest. Side effects already emitted before a regression is detected (tickets filed, dashboards cached, notifications sent during the shadow/canary window) cannot be un-sent; the design's own 'rollback blind spots' risk is mitigated, not eliminated.
